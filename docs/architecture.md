# Undertow — архитектурные решения

Личный проект, один пользователь (я), Windows. Не публикуется, не распространяется.
Цель: красивый и удобный десктопный стриминг-клиент с полным каталогом —
новинки, чарты, популярные треки, плейлисты, «моя волна».

Дата фиксации решений: проверки выполнялись локально в этой папке.

---

## 1. Источники музыки: что проверено руками

| Источник | Статус | Вердикт |
|---|---|---|
| **Яндекс.Музыка** (неоф. API `api.music.yandex.net`) | хост отвечает 404 на `/` (живой), нужен OAuth-токен | **основной источник**: каталог РФ, новинки, чарты, FLAC |
| **YouTube / YouTube Music** (через `yt-dlp`) | `2026.10.26`, поиск + прямая ссылка + `206 Partial Content` за 0.33 с | **второй источник / фолбэк**: нет ни одного «дырявого» трека |
| **Spotify** (через `librespot`) | мёртв: Spotify сменил выдачу ключей, `audio key error 0 1`, обхода нет (issue #1649) | **отказ** |
| **youtubei.js** (v18.3, чистый JS) | форматы приходят **без** `url` и `signature_cipher` (SABR + PO token), `decipher` падает | **отказ**, только как источник метаданных |
| SoundCloud (api-v2) | хост отвечает 401 | опционально, позже |
| VK/BOOM (неоф.) | `api.vk.com` жив | опционально, позже |

Вывод: **два провайдера достаточно**, чтобы покрыть «всё». Яндекс даёт нормальные
метаданные и локальную выдачу, YouTube закрывает то, чего в Яндексе нет
(редкие релизы, зарубежка без лицензии в РФ, лайвы, ремиксы).

> Правовая сторона: это клиент для **своей** подписки и личного прослушивания.
> Никакой раздачи, публичного доступа и обхода платного контента.

## 2. Стек

**Electron 45 + electron-vite 6 + Vite 8 + React 19 + TypeScript 7**, БД — `better-sqlite3` 13.

Почему не Tauri: Rust в системе не установлен (`cargo`/`rustc` отсутствуют),
установка тулчейна — ~1.5 ГБ и полчаса ради 40 МБ экономии бинарника.
Для личного приложения Electron-овергеда не важна, зато Chromium из коробки
играет Opus/WebM/AAC/FLAC и даёт Web Audio API для кроссфейдов и эквалайзера.

Структура:

```
src/main/       // Electron main: окна, провайдеры, yt-dlp, локальный аудио-сервер, SQLite
src/preload/    // типизированный мост IPC
src/renderer/   // React UI (Vite)
spikes/         // одноразовые проверки гипотез (не входит в сборку)
```

## 3. Абстракция провайдера

Всё, что умеет отдавать музыку, реализует один интерфейс. UI ничего не знает про
конкретный сервис.

```ts
export interface Track {
  id: string;            // "ym:12345" | "yt:dQw4w9WgXcQ"
  provider: 'yandex' | 'youtube';
  title: string;
  artists: string[];
  album?: string;
  durationSec: number;
  coverUrl?: string;
  year?: number;
  explicit?: boolean;
}

export interface Provider {
  id: string;
  isAuthenticated(): Promise<boolean>;
  /** Вход: токен из настроек (Яндекс) либо no-op (YouTube) */
  authenticate(secret?: string): Promise<void>;

  search(query: string, opts?: { limit?: number; offset?: number }): Promise<Track[]>;
  home(): Promise<Section[]>;              // «Новинки», «Чарты», «Для тебя»
  charts(region?: string): Promise<Section[]>;
  artist(id: string): Promise<ArtistPage>;
  album(id: string): Promise<AlbumPage>;
  playlist(id: string): Promise<PlaylistPage>;
  myPlaylists?(): Promise<Playlist[]>;     // то, что уже собрано в сервисе

  /** Разрешение в playable-URL. Живёт ~1 мин (Яндекс) / до истечения (YouTube). */
  resolveStream(track: Track, quality?: 'normal' | 'high' | 'lossless'): Promise<ResolvedStream>;
}

export interface ResolvedStream {
  /** URL для <audio>, либо внутренний прокси, если нужна расшифровка/свои заголовки */
  url: string;
  mime: string;
  bitrateKbps?: number;
  /** Прогрев следующего трека: адрес протухает, кэшировать нельзя */
  expiresInSec?: number;
}
```

У каждого провайдера есть **кэш разрешённых ссылок на 30–50 с**, чтобы перемотка
не дёргала API заново.

## 4a. Потолок качества (измерено)

| Источник | Что реально отдаёт | Как проверено |
|---|---|---|
| YouTube | Opus ~130–160 kbps VBR (itag 251), AAC 130k (itag 140) | `yt-dlp -F`: выше 251 в списке ничего нет |
| Яндекс | MP3 320 kbps | `download-info` содержит только mp3 192/320 |

FLAC у Яндекса: `/get-file-info?quality=lossless` на трёх треках (Molchat Doma,
Billie Eilish, Radiohead) отвечает `codec: mp3, bitrate: 320` — сервер понижает
качество, значит lossless не входит в тариф аккаунта.

В коде есть автопроба: перед первым треком спрашиваем FLAC; если появится (`transport: raw`) —
включается сам, если 3 трека подряд без FLAC — проба гаснет до перезапуска.
Ветка `transport: encraw` (AES-128-CTR, ключ в ответе) распознаётся и логируется,
но потребует локального расшифровывающего прокси — тогда и включим.

## 4. Аудио-конвейер

Все треки идут через локальный прокси (`src/main/audioProxy.ts`):
`http://127.0.0.1:<порт>/a?s=<секрет>&u=<base64url(прямой url)>&ct=<mime>`.

Зачем прокси обязателен:

- ни `googlevideo.com`, ни Яндекс не отдают `Access-Control-Allow-Origin`
  (проверено curl-ом: в ответе 206 нет ни одного ACAO-заголовка);
- без CORS `MediaElementAudioSourceNode` отдаёт в граф тишину — то есть
  кроссфейд и нормализация были бы невозможны;
- прокси ставит CORS-заголовки сам, пробрасывает `Range`/`Content-Range`/206
  (перемотка работает) и подменяет `application/octet-stream` от Яндекса
  на известный mime, иначе декодер может отказаться от потока;
- в нём же позже появится расшифровка lossless (`transport: encraw`,
  AES-128-CTR, nonce = 12 нулевых байт, ключ в ответе `/get-file-info`).
- защита: случайный секрет на сеанс + allowlist хостов (googlevideo,
  *.yandex.net), чтобы порт нельзя было использовать как открытый прокси.

Обработка звука (`src/renderer/src/audio/engine.ts`):

```
el[0] ─ MediaElementSource ─ gain0 ┐
                                   ├─ masterGain ─ компрессор-лимитер ─ analyser ─ выход
el[1] ─ MediaElementSource ─ gain1 ┘
```

- два элемента — чтобы прогреть следующий трек и переключаться по кривой;
- gapless: переключение на остатке 0.16 с, рампы 20 мс, зазора нет
  (замер: позиция ни разу не встала дольше одного опроса 25 мс);
- кроссфейд 3/6/12 с: равномощные кривые `cos/sin`, обе дорожки слышны
  одновременно (замер: 0.79/0.61 → 0.34/0.94 по ходу фейда);
- переключение атомарно: у него есть номер (`switchToken`), и отложенный
  `commitSwitch` применяется только если номер не сменился и следующим в
  очереди всё ещё идёт тот же трек. Раньше быстрые «в самый конец» два раза
  подряд давали рассинхрон: в панели следующий трек, в динамиках предыдущий;
- соседний слот обязан содержать именно `queue[index + 1]`: если там устаревший
  трек (например, остался от прошлой очереди), слот освобождается и трек
  стартует как обычно, а не «доигрывается» чужой;
- при смене трека старый поток в слоте глушится и очищается сразу, ещё до
  готовности нового URL — иначе при подмене (до ~3.5 с на поиск) слышно
  предыдущий трек, хотя панель уже показывает новый (`clearSlot`);
- нормализация: RMS с `AnalyserNode` ~10 раз в секунду, цель −18 dBFS,
  сглаживание 0.06 за кадр, гейт ниже −45 dB, буст не больше +12 дБ,
  на выходе лимитер (−6 дБ, ratio 6) от клиппинга.

## 4b. Библиотека и лайки

Локальное хранилище — `%APPDATA%/Undertow/library.json`
(`src/main/library.ts`): без нативных модулей, запись атомарная (tmp + rename)
с задержкой 250 мс, история ограничена 2000 записями.

Лайки Яндекса (проверено на аккаунте, 727 треков):

| Действие | Запрос |
|---|---|
| список лайков | `GET /users/{uid}/likes/tracks` → `result.library.tracks[{id, albumId, timestamp}]` |
| поставить лайк | `POST /users/{uid}/likes/tracks/add-multiple?trackIds=<id>` |
| снять лайк | `POST /users/{uid}/likes/tracks/remove?trackIds=<id>` |
| метаданные треков | `GET /tracks?track-ids=a,b,c&with-positions=false` (пачками по 100) |

Грабли:

- `uid` в пути **обязан** быть настоящим uid из `/account/status`. С произвольным
  числом сервер отвечает `403 ownerOtherwiseUserBindingError`.
- тело запроса на лайк не читается: параметр должен идти в query string
  (`trackIds=`), иначе `400 validate: trackIds is not set`.
- старый путь `POST /users/{uid}/likes/tracks/{trackId}` теперь отдаёт 404.

Поведение лайка: локально сохраняется всегда, на сервер уходит только для
`ym:`-треков при активном Яндексе; если сервер отказал — лайк остаётся локальным
и UI показывает предупреждение.

Импорт: `GET` списка (727 id) → отбрасываем уже известные → тянем метаданные
пачками → `mergeLikes` сортирует по времени проставления. Первый запуск с
пустой библиотекой и активным Яндексом запускает импорт сам.

## 4c. Подмена яндексовских треков на YouTube

Библиотека переживает подписку: без Яндекса треки `ym:` ищутся на YouTube
(`src/main/fallback.ts`) и играют оттуда.

Когда включается:

- токена нет или Плюс неактивен — сразу;
- Яндекс активен, но `resolve` упал (в том числе вернул превью — тогда Плюс
  гасится до перепроверки);
- в обоих случаях нужны метаданные трека, поэтому `resolve` из рендерера
  передаёт объект `Track` (`resolve(id, fresh, meta)`). Без меты — понятная ошибка.

Как ищется:

1. **быстрый путь** — один запуск yt-dlp (`ytSearchResolve`): `ytsearch1:`
   сразу печатает id, название, канал, длительность, формат и готовую ссылку
   на звук через `--print` шаблон. Один процесс вместо двух — это ~3.5 с
   вместо ~5 с. Название и Δдлительности проверяются строже (score ≥ 0.5
   и Δ ≤ 12 с), потому что сравнивать не с чем;
   `PYTHONIOENCODING=utf-8` обязателен — без него кириллица приходит
   в консольной кодировке Windows и превращается в мусор;
2. параллельно с ним идёт обычный поиск метаданных (`--flat-playlist`, 2
   формулировки). Если быстрый путь промахнулся, кандидаты уже собраны и
   не нужно ждать ещё один круг: так худший случай ~6.5 с, а не ~9 с;
3. формулировки: `artist + title`, `title + первый артист`,
   `первый артист + название без скобок`, просто название. Одного запроса
   мало: yt-dlp отдаёт пусто на смеси латиницы с кириллицей («Whole Lotta
   Swag 68 парень» → 0 результатов, «68 парень» → находит сразу). Второй круг
   запускается только если первый не дал уверенного совпадения;
4. кандидаты оцениваются как `совпадение названия ± бонусы − Δ/120`:
   +0.15 если исполнитель есть в названии/канале, +0.18 за канал `… - Topic`
   (это автозагруженный альбомный звук), +0.12 за official/records;
   ×0.8 если исполнитель вообще не упомянут, ×0.55 за чужую версию
   (remix/slowed/8-bit/acoustic/cover/live/instrumental/минус/…);
5. принимается лучший с оценкой ≥ 0.34 (или Δ ≤ 5 с при 0.2);
   приблизительный вариант (Δ ≤ 25 с, исполнитель совпал, не чужая версия)
   играет с пометкой в тосте. Если ничего — честная ошибка: лучше не играть,
   чем играть чужое.

Повторные запросы схлопываются: если поиск по треку уже идёт (прогрев по
наведению в списке или предзагрузка следующего), клик ждёт его результат,
а не запускает второй yt-dlp.

**Версии трека.** Кнопка «другой вариант» у любого трека открывает панель
`src/main/versions.ts`: это уже не поиск другой загрузки исходника, а подборка
*переделок* — ремиксы, каверы, оркестровки, рок-версии, hardtekk, phonk,
замедленные и ускоренные варианты.

- семь параллельных поисков `youtube.search` (база + remix/cover/orchestral/
  rock version/hardtekk/phonk), артист подставлен в каждый запрос и обязан
  встречаться в названии или канале — иначе на распространённые названия
  («Witch Doctor») прилетают одноимённые чужие песни;
- фильтр по словам названия (не меньше половины слов), отсечение роликов
  короче 0.3× и длиннее 3× оригинала, дедупликация по `videoId` и по
  названию без «official video/audio»;
- метка жанра из названия; в списке не больше 5 версий одной метки и не больше
  2 «дешёвых» перезаливов (замедлено/ускорено/8D/bass boost);
- кэш 15 минут по «название|артист», до 24 результатов.

В панели над списком — фильтр-чипы по меткам с количеством («все», «ремикс»,
«кавер», «оркестр»…). Чипы переносятся на новые строки: горизонтальная
прокрутка колесом мыши недоступна, и часть меток иначе было бы не достать.
Блок чипов прилипает к верху панели при скролле, повторный клик по активному
чипу снимает фильтр.

Клик по версии — обычное воспроизведение: очередь собирается из всего списка
версий (выбранная первой), поэтому их можно листать вперёд-назад. Кнопка «+»
в строке версии кладёт её в конец очереди, не переключая текущий трек.
Панель привязана к исходному треку: переключение на другой трек закрывает её
и сбрасывает базу (`versionBaseRef` + `versionIdsRef`), поэтому список версий
не «залипает» с прошлой песни. Первая
строка панели — «оригинал — <трек>», она возвращает исходную запись; если же
играет автоподмена, показывается ещё и «вернуть исходную запись»
(`fallback.unpin` + перезапуск).

Старый ручной выбор копии из `yt-map.json` (`fallback.pin`) остался в API и
работает для `fallback:*`, но в интерфейсе кнопка теперь ведёт в версии.

Как это показано в плеере (`engine.displayOf` + `emitCopy` → `onCopy`):

- **выбран вручную** (`variant: true`): главная строка — название копии, под
  ней приглушённое «оригинал: …». Копия живёт как самостоятельный трек с id
  `yt:<videoId>`, поэтому её можно лайкнуть: сердечко относится именно к копии
  и в библиотеке появляется отдельная запись с её названием;
- **автоподмена** (Яндекс недоступен): главная строка — трек из очереди, под
  ней «копия: …», сердечко относится к записи в библиотеке.

Первым пунктом меню при закреплённом варианте идёт «вернуть оригинал»
(`fallback.unpin` + перезапуск), он появляется только если вариант выбран
вручную (`Mapping.forced`), а не найден автоматически.

Результат пары кэшируется в `%APPDATA%/Undertow/yt-map.json`
(до 5000 записей, старые вытесняются). Повторный запуск того же трека — 0 мс.
Если видео исчезло, кэш сбрасывается и поиск делается один раз заново.
Ссылка на звук YouTube живёт часами, поэтому кэш ссылок держим 10 минут
(у Яндекса — 50 с, там ссылки короткоживущие).

Прогрев, когда он срабатывает: наведение курсора на строку в списке
(120 мс задержки, чтобы не дёргать yt-dlp при проезде мимо) и предзагрузка
следующего трека в очереди. Поэтому «долгий старт» после клика остаётся только
у треков, которые не проходили проверку и заново ищутся полным перебором — для
них есть кнопка «другой вариант», где можно найти версию получше.

Как это видно в интерфейсе: рядом с названием в плеере стоит значок источника
(`YM` / `YT`) и компактная подпись формата (`OPUS 144`, `MP3 320`); при старте
трека вылетает тост с найденным названием, а в библиотеке появляется плашка
«Яндекс отключён — треки будут играть копиями с YouTube».

Отладка без потери токена: `UNDERTOW_NO_YANDEX=1 npm run dev` — Яндекс считается
отключённым, но токен остаётся в секретах.

## 4d. Очередь и перемешивание

Очередь живёт в рендерере (`AudioEngine.queue`), main про неё ничего не знает:
это чисто порядок воспроизведения, а не библиотека.

API движка: `getQueue/getIndex/isShuffled`, `moveInQueue(from,to)`,
`removeFromQueue(at)`, `addToQueue(track, 'next'|'end')`, `playAt(at)`,
`setShuffle(on)`. Любое изменение рассылается в UI через `onQueue(queue, index,
shuffled)` — App хранит копию для панели.

Правила, которые легко сломать:

- текущим остаётся трек, а не позиция: при перестановке `index` пересчитывается
  по `queue.indexOf(current)`, иначе перетаскивание играющего трека уводило бы
  воспроизведение на соседний;
- любая смена текущего трека рассылает `onQueue`: и автоматический переход
  (`commitSwitch`), и ручной `hardSwitch` (кнопки next/prev, клик по строке
  очереди). Раньше `hardSwitch` молчал, и панель показывала предыдущий трек;
- удаление играющего сразу запускает следующий (`hardSwitch` на ту же позицию),
  удаление выше по списку сдвигает `index` на единицу;
- при добавлении трек, который уже есть в очереди, не дублируется — приходит
  ошибка-тост;
- перемешивание тасует только хвост: сыгранное и текущий трек остаются на
  местах. Исходный порядок хвоста запоминается (`shuffleTail`), поэтому
  выключение тумблера возвращает его; любая ручная правка очереди сбрасывает
  это воспоминание (иначе «вернуть как было» смешало бы уже изменённый список);
- если перемешивание включено, новая очередь (`setQueue`) стартует тоже вперемешку.

Интерфейс: кнопка со счётчиком в правой части плеера открывает панель
(`QueuePanel.tsx`) — список с ручками перетаскивания (HTML5 drag & drop),
удалением по наведению, отметкой играющего трека и кнопкой «перемешать».
Добавить трек в очередь можно кнопкой «+» в любой строке списка
(`TrackList.onAddToQueue`), трек всегда уходит в конец.

### Очередь между запусками (`src/main/queueStore.ts`)

Раньше очередь жила только в памяти рендерера и пропадала при закрытии. Теперь
`%APPDATA%/Undertow/queue.json` хранит состав (до 500 треков), текущий индекс,
флаг перемешивания, позицию в секунде и время сохранения.

- рендерер при изменении очереди шлёт `queue:save` (дебаунс 600 мс), а раз в
  5 секунд — лёгкий `queue:time` только с индексом и временем;
- main пишет файл атомарно (tmp + rename) с задержкой 500 мс;
- на старте `queue:get` возвращает состояние, `AudioEngine.restore()` ставит
  состав и позицию **в паузе**: звук не включается сам, но трек уже в плеере;
  кнопка play создаёт аудиограф (после restore его нет) и начинает ровно с
  сохранённой секунды (`pendingSeek` в `startActive`);
- очередь старше двух недель не восстанавливается — за это время она уже
  неактуальна; битые записи и треки без id/title отсекаются при чтении;
- восстановленная очередь не запускает дозаправку `radio`/`flow`: флаги сессий
  живут в рендерере и после перезапуска пустые;
- кнопка-корзина в шапке очереди чистит всё: `engine.clearQueue()` освобождает
  оба аудиослота, `queue:clear` удаляет `queue.json`, плеер возвращается в
  «Ничего не играет».



### Оживление интерфейса (`styles.css`)

- у плеера класс `.playing`, пока идёт звук: бегущая линия по верхней кромке,
  свечение обложки на `--rms` (RMS из снапшота), мини-эквалайзер в углу
  обложки, пульс кнопки play, блик по прогресс-бару и точка на его конце;
- страницы входят `riseIn`, первые 14 строк списка — `rowIn` с задержкой
  (на 700 строках библиотеки это не тормозит: анимируются только первые);
- карточки: подсветка рамки и лёгкий зум обложки, боковое меню получило
  градиентную полоску активного пункта, панель очереди и тосты входят снизу;
- всё это отключается при `prefers-reduced-motion: reduce`.

Анимации плеера сделаны так, чтобы не дёргаться:

- бегущая линия — это широкий слой (300 %), у которого двигается только
  `transform`; `background-position` (перерисовка каждого кадра) не используется;
- эквалайзер — фиксированные 12 px с `transform: scaleY()`, а не анимация
  `height` (она вызывала пересчёт раскладки на каждом кадре);
- пульс кнопки play — кольцо-псевдоэлемент со `scale`, а не `box-shadow`;
- «дыхание» обложки — `opacity` слоя от `--rms`, бокс-тень статична;
- у всех анимированных слоёв `will-change`, а в `webPreferences` стоит
  `backgroundThrottling: false` — окно без фокуса больше не замедляет
  композитор.

## 4e. Главная от библиотеки (подборки)

Раньше главная была одинаковой для всех: `landing3` Яндекса + лента YouTube.
Теперь при достаточной библиотеке (`≥ 15` лайков, `src/main/recommend.ts`) она
собирается из своих данных. Модели нет — только счётчики и фильтры, поэтому
результат всегда можно объяснить словами.

Сигналы и секции:

| Секция | Откуда берётся |
|---|---|
| «Продолжить слушать» | история, без повторов, 12 треков |
| «Ещё от <артист>» | артисты, которые встречаются в лайках чаще всего (`/artists/{id}/tracks`) |
| «Давно не слушали» | лайки, не игравшие 90+ дней (или никогда) |
| «Альбом «<название>»» | альбомы, откуда больше всего лайков (`/albums/{id}/with-tracks`) |
| «Новое от <артист>» | свежий альбом любимого артиста (`/artists/{id}/direct-albums`) |

Артисты и альбомы берутся не из лайка как такового, а из метаданных трека:
`/tracks?track-ids=` отдаёт `artists[0].id`, `albums[0].id/title/year`
(`yandex.tracksMeta`). Идентификаторов у YouTube-лайков нет, поэтому профиль
строится по яндексовой части библиотеки — если её мало, главная откатывается
к общей ленте.

Фильтры, без которых подборка раздражает:

- из личных секций убираются лайкнутые треки (это уже есть в избранном) и всё,
  что играло последние 45 дней — иначе выходило «ещё от артиста» из тех же
  самых песен;
- общий `used` set не даёт треку попасть сразу в «ещё от» и «новое от»;
- секция не показывается, если в ней меньше 4–5 треков;
- альбомов и артистов берём по 2–3, иначе главная превращается в бесконечную
  простыню.

Кэш: `%APPDATA%/Undertow/home-rec.json`, TTL 6 часов, сбрасывается, если число
лайков изменилось больше чем на 10 (импорт пачки лайков) или по кнопке
«обновить подборку» (`home:refresh` → `providers.home(true)`). Сборка занимает
~1.3 с и 5–9 запросов, из кэша — 0.3 с.

Без Яндекса (`recommend.localSections`) остаются «Продолжить слушать» и «Давно
не слушали» — они считаются из локального JSON и работают всегда.

Нюанс старта: рендерер зовёт `home()` параллельно с `state()`, а признаки
«валиден/есть Плюс» ставит `refreshYandex()`. Добавлен `ensureYandexChecked()` в
`home/search/resolveStream`, иначе первая лента собиралась так, будто Яндекса
нет, и подборки не появлялись до перезагрузки.

---

**Главная: до шести артистов и раскрывающиеся секции.** В режиме с Плюсом
`compose` собирает до шести секций «Ещё от …» (`ARTIST_SECTIONS`), у каждой —
свой аватар, подпись «27 альбомов · 60 треков» (из `yandex.artistPage`,
заменившего `artistTracks`) и до 20 новых треков (`ARTIST_TRACKS`). Без Плюса
`localHome` делает то же самое через YouTube Music: до шести артистов с
`coverUrl`/`subtitle` и по 16 треков, страницы тянутся по три параллельно
(`mapLimit`), а треки не повторяются между секциями (`used`). В `Section`
появились необязательные `subtitle` и `coverUrl` (кэш `CACHE_VERSION 5`).

В `Home.tsx` любая секция-список по умолчанию показывает 8 строк, а под ней
кнопка «показать все N / свернуть» (`expand-btn`, состояние в `expanded`).
Клик по-прежнему ставит в очередь **всю** подборку: `TrackList` получил
`playContext`, иначе при свёрнутом списке в очередь попадали бы только 8
треков. В шапке секции — «слушать всё» (пилюля, всегда видна) и ссылка
«артист →/альбом →». Альбомные и «Новое от …» секции тоже получили подпись и
обложку. Внизу `.scroll` добавлен отступ (`::after` + `scroll-padding-bottom`),
чтобы последняя строка не пряталась под плеером.

**Навигация и ярлыки на главной.** Над лентой — липкая полоса чипов
(`.chips-wrap`, `position: sticky; top: -26px` — ровно верхний padding
`.scroll`, поэтому при скролле она прилипает вплотную к заголовку окна, а не
висит с зазором; в прилипшем состоянии добавляется класс `stuck` с тенью):
по одному на секцию, короткие подписи (`chipLabel`: «Продолжить», имя артиста,
«Альбом «…»»), активный чип залит бирюзовым и подсвечивается по скроллу.

Если окно узкое и чипы не влезают, полоса листается: стрелки `‹ ›`
(`.chips-nav`) появляются только когда есть что листать (`syncEdges` по
`scrollWidth - clientWidth`, обновляется на `ResizeObserver`), край fading-маска
включается классами `has-left`/`has-right`. Стрелки стоят в flex-потоке, а не
поверх чипов, нажатый чип центрируется (`centerChip`), поэтому активный пункт
не прячется под краем. Прокрутка колесом/тачпадом работает и сама по себе. Переход считается от **высоты** полосы, а не от её
текущего низа (`jumpTo`): в самом верху страницы она ещё не прилипла, из-за
чего первые переходы раньше останавливались на 80 px выше. Активная секция
ищется по `getBoundingClientRect().top`, а не по `offsetTop` — у `offsetParent`
не обязательно скролл-контейнер, из-за чего подсветка отставала на одну
секцию; у самого дна подсвечивается последняя.

В артист-секции под шапкой — полоска из четырёх обложек альбомов
(`.album-strip > .album-thumb`, с годом), клик открывает настоящий альбом.
Данные берутся из `Section.albums` (заполняется из `page.albums` в обоих
режимах, `CACHE_VERSION 6`), а если их нет — из полей `album`/`albumId`
треков секции. В hero добавлены ярлыки источника и размера подборки
(`.hero-tags`) и кнопки «Об артисте»/«Альбом».

## 4f. Страницы артиста и альбома

Подборки ссылаются на исполнителей и альбомы, поэтому появились две страницы
(`BrowseView.tsx`, одно представление на два случая):

- `page:artist` → `yandex.artistPage`: параллельно `/artists/{id}` (имя, обложка,
  `counts.directAlbums`), `/artists/{id}/tracks` (60 треков) и
  `/artists/{id}/direct-albums` (12 альбомов);
- `page:album` → `yandex.albumPage`: `/albums/{id}/with-tracks`, сборники
  склеиваются из `volumes`.

Входы: ссылка «артист →» / «альбом →» в заголовке персональной секции (`rec-artist-*`,
`rec-album-*` — id уже есть в id секции) и карточки ленты Яндекса, которые теперь
несут настоящий id (`ym-album:<id>` / `ym-artist:<id>`) вместо прежнего
`ym-card:<title>`. Карточки YouTube по-прежнему показывают «скоро».

Навигация — стек (`browseStack` в App): артист → альбом → «назад» возвращает на
артиста, а не на главную; повторный «назад» с вершины стека закрывает страницу.
Клик по «Главная» в сайдбаре стек сбрасывает. «Слушать всё» на странице ставит в
очередь именно её треки, так что дальше работают очередь и перемешивание.

Без Яндекс Плюса страницы недоступны: `requireYandex()` возвращает понятную
ошибку, `BrowseView` показывает её вместо пустого экрана.

## 4g. Обратная связь: скрыть секцию, открыть исполнителя

**Скрытие секций.** Крестик в заголовке секции убирает её с главной и
запоминается в `%APPDATA%/Undertow/rec-prefs.json` (`{ version, hidden: string[] }`,
пишется атомарно через временный файл). Скрывать можно любые секции, включая
YouTube-шные (`explore-0`), поэтому фильтр стоит не в сборке подборки, а в самом
конце `providers.home()` — `recommend.applyPrefs()`.

Из этого следует важное: **скрытие не сбрасывает кэш подборки**. Секции
собираются и кэшируются целиком, фильтр применяется при выдаче, поэтому «вернуть»
работает мгновенно и не требует заново дёргать API. Кнопка «вернуть секции (N)»
появляется в шапке, только когда что-то скрыто, и чистит список.

**Исполнители как ссылки.** У `Track` есть `artistId` (первый исполнитель) и
`artists: { id?, name }[]` — полный список с id каждого. Отдельный компонент
`ArtistLine.tsx` рисует имена через запятую, и каждая ссылка ведёт на своего
артиста: в строках списков (главная, поиск, библиотека, страница альбома) и в
плеере под названием трека. У YouTube-треков id нет — имя остаётся текстом, у
старых записей `library.json` списка тоже нет, работает фолбэк на `artistId`.

Старые записи в `library.json` сохранились без `artistId`, поэтому ссылки
появляются у треков, сыгранных/сохранённых после изменения (снимок кэша
подборок тоже пришлось пометить версией: `CACHE_VERSION` в `recommend.ts` —
сначала 2 для `artistId`, затем 3 для `artists`, иначе в кэше лежали треки
без новых полей и ссылки просто не появлялись).

## 4h. Дозаполнение библиотеки (обогащение)

Лайки и история хранят снимок трека на момент сохранения. Поля `artistId` и
`artists` появились позже, поэтому у старых записей не работали ссылки на
исполнителей — в истории это было видно сразу.

`providers.enrichLibrary()` берёт треки, у которых нет `artists`, режет их на
пачки по 100 и зовёт `/tracks?track-ids=` (`yandex.tracksMeta`), после чего
`library.patchTracks()` переписывает записи в лайках и истории (атомарно, тем же
дебаунсом, что и обычное сохранение). Заодно дописываются `album` и `coverUrl`.

Вызывается из рендерера один раз при старте, в фоне — интерфейс не ждёт.
Замер: 728 лайков + 102 записи истории, ~350 реально нужных id — 1.1 с, 4 запроса.

Треки YouTube остаются без исполнителей: у них нет `artistId`, ссылку вести не на
что, имя остаётся текстом.

**Гонка при проверке токена.** Обогащение на старте сначала не срабатывало:
`refreshYandex()` ставил `checkedAt` в начале, а флаги `yandexValid/yandexPlus` —
только после ответа API. Параллельный `ensureYandexChecked()` видел `checkedAt`
и решал, что всё уже проверено, `yandexReady()` возвращал false, обогащение
выходило. Теперь `refreshYandex()` переиспользует один in-flight промис, а
`ensureYandexChecked()` его дожидается (или завершается сразу, если проверки нет).

## 4i. Альбом из трека и «радио артиста»

**Переход к альбому.** В `Track` появилось `albumId` (из `albums[0].id`), его
дозаполняет то же обогащение библиотеки. Ссылки на альбом два: кнопка-пластинка
в строке списка (появляется при наведении рядом с «+» и сердцем) и название
альбома после имён исполнителей в плеере: `Aarne, Toxi$ · SLAANG`.

В списках под кнопку альбома зарезервирован слот: у треков без `albumId`
(YouTube) на этом месте пустой `span` фиксированной ширины, иначе у таких строк
уезжали бы колонки сердца и длительности. Проверено: плюс 1124 px, пластинка
1151, сердце 1178, время 1216 — одинаково во всех строках.

**Год выпуска.** `Track.year` приходит из Яндекса (`album.year`) и со страниц
альбомов YouTube Music. У песен YouTube Music года нет — он лежит в шапке
альбома, поэтому `youtube.fillYears()` ищет альбом по названию (кэш навсегда) и
проставляет год трекам в artist-страницах и «Течении». В списках год стоит в
подписи после исполнителя, в плеере — отдельным чипом.

**Проверка id перед Яндексом.** Яндекс принимает любой id и на `UC…` отвечает
пустой страницей «Артист» — из-за этого ссылка на артиста из «Течения» вела в
пустоту. Теперь `artistPage`/`albumPage`/`artistRadio` отдают Яндексу только
числовые id, а пустой ответ трактуют как повод перейти на YouTube Music.

**Радио артиста** (`providers.artistRadio`). Отдельного радио-эндпоинта без
client-id нет, поэтому очередь собираем сами:

1. топ артиста — `/artists/{id}/tracks` (50), в очередь идёт первые 14;
2. похожие — `/artists/{id}/similar?limit=10` → у семи из них берём по 24 трека;
3. чередование по кругу: по одному треку от каждого похожего, пока не наберётся
   90 уникальных (дедуп по id, свои треки артиста исключены из этой части);
4. `setQueue` получает готовый список — дальше работает обычная очередь.

Кнопка «Радио» стоит рядом с «Слушать всё» на странице артиста, во время сборки
подписана «собираю…». Замер: 90 треков за ~0.5 с, 8 запросов.

### Течение (`src/main/flow.ts`)

Бесконечный поток рекомендаций по библиотеке, отдельная вкладка в сайдбаре.
Не плейлист: очередь достраивается сама, пока играет.

- **семя** — `artistWeights()` из библиотеки (лайк = 3, прослушивание = 1):
  из топ-16 берутся 6 с случайным разбросом веса (0.4–2.0) и перемешиваются,
  иначе каждая пересборка начиналась с одного и того же артиста; профили
  `youtube.musicArtist()` дают обложки и `related`;
- **соседи** — до 10 «похожих» с этих профилей, у них забираются треки
  (по 3 запроса параллельно, всего ~16 артистов);
- **фильтр** — всё, что уже есть в библиотеке, из пулов выкидывается по id;
  дубликаты между пулами ловятся по множеству слов названия (`keyOf`);
- **чередование** — по одному треку с каждого артиста по кругу, один и тот же
  артист не звучит дважды подряд (отложенные треки возвращаются в пул); пулы
  перемешиваются, и каждый круг начинается со следующего пула (`cursor`),
  чтобы порядок артистов не повторялся; новая сборка не начинается тем же
  артистом, что и предыдущая;
- **редкое своё** — примерно один трек на двадцать берётся из лайков, но не
  чаще, чем раз в 12 треков, чтобы знакомое не вытесняло новое;
- **дозаправка** — как у радио: `onQueue` в рендерере при остатке ≤ 6 треков
  зовёт `flow:more` (20 треков), флаг `flowRef` сбрасывается при обычном
  `playTrack`.
- **второй круг** — когда пулы исчерпаны, `expand()` берёт `related` от первых
  пяти артистов и добавляет до 6 новых пулов.

Старт — 30 треков за ~5.5 с (16 профилей YouTube Music + до 8 запросов
«год альбома»). Визуализация: пока поток играет, `AudioEngine.spectrum()` отдаёт
спектр из AnalyserNode, и FlowView рисует зеркальные радиальные полосы вокруг
орбиты; `--level` (RMS) задаёт «дыхание» свечения и масштаб иконки. В паузе и до
старта страница статична: анимации висят на классах `.live`. Клик по карточке
артиста в блоке «Откуда течёт» запускает обычное радио этого артиста
(`artistRadio`), поэтому поток и радио живут в одном разделе.

### Новинки (`src/main/releases.ts`)

Страница «что вышло у тех, кого вы слушаете». Артисты выбираются тем же
`artistWeights()` (лайк = 3, прослушивание = 1), дальше 14 профилей
`youtube.musicArtist()` параллельно по три — это даёт *канонический* список
релизов, без путаницы одноимённых артистов.

- **свежий релиз** — самый поздний год в `profile.albums` (сортировка по году,
  внутри года сохраняется порядок YouTube Music; тип `single`/`ep`/`album`
  парсится из подписи карточки);
- **точная дата** — из iTunes Search API (Apple Music, `country=RU`, без ключа):
  запрос по артисту, затем совпадение *того же* релиза по названию (по словам,
  а не подстрокой) при точном имени артиста. Если iTunes отдал однофамильца
  или такого релиза у него нет, дата остаётся годом — YouTube Music считался
  и считается источником истины;
- **прослушивания** — `ytSearch(«артист + название», 5)`; берётся ролик, где
  совпадают и название (не меньше половины слов), и артист. Число — это
  просмотры YouTube, поэтому в интерфейсе оно всегда подписано `YouTube`;
  нет совпадения — прослушивания не показываются, а не подставляется чужое;
- **кэш** — `%APPDATA%/Undertow/releases.json`, TTL 6 часов, кнопка «обновить»
  в шапке игнорирует его (`releases:list` с `force`). Сборка холодная ~20 с
  (14 профилей + 14 ответов iTunes + 14 поисков yt-dlp), из кэша — мгновенно,
  поэтому при первом заходе показываются скелетоны.

В интерфейсе релизы сгруппированы по годам (у части записей известен только
год; группировка по месяцам давала два блока «2026» подряд), свежие (≤ 30 дней)
помечены `new`. Клик по обложке/названию открывает альбом (`yt-album:MPREb…`),
кнопка ▶ запускает первый трек, имя артиста — его страницу.

**Дозаправка** (`src/main/radio.ts`). Сессия радио живёт в main по artistId и
помнит курсор страниц у каждого похожего артиста (`cursor`, до `MAX_PAGES = 8`),
общий `used` set и буфер `pending` — скачанные, но ещё не отданные треки, чтобы
не терять остаток страницы (без буфера каждый запрос качал 7 страниц и отдавал
только 30 треков).

Рендерер следит за позицией в `onQueue`: как только до конца очереди остаётся
меньше 5 треков, вызывает `radio:more` → `engine.appendQueue()` дописывает
порцию (30 треков, дубликаты отбрасываются). Флаг `radioBusy` не даёт запустить
две дозаправки сразу, а `playTrack` (обычный запуск из списка) сбрасывает
`radioRef`, поэтому обычные очереди не дозаправляются.

### Жанры и течение по жанрам (`src/main/genres.ts`)

Жанр есть только на уровне артиста/альбома, поэтому поток фильтруется по
артистам, а не трекам. Источников два, гибрид:

- **iTunes Search API** (`primaryGenreName`, страна RU) — работает всегда и
  сразу по-русски: `Хип-хоп`, `Хард-рок`, `Поп`; берётся самый частый жанр
  по альбомам, и если альбомов несколько — он должен подтвердиться хотя бы
  дважды (иначе однофамилец с одним релизом приносил «регги» рэперу);
- **Яндекс** (`/artists/{id}.genres`) — только при сохранённом токене, отдаёт
  слаги (`rusrap`, `foreignrap`). Если артист есть в Яндексе, верим его первому
  жанру: iTunes для русских рэперов часто находит однофамильцев.

Слаги и человеческие названия сводятся к фиксированным корзинам (`BUCKETS`:
хип-хоп, рок, поп, электроника, R&B и соул, инди, джаз, классика, саундтреки,
фолк, регги, латина, блюз, шансон) — так в чипах не появляются «Зимние
праздники». Список жанров **динамический**: считаются артисты библиотеки с
этим тегом и их суммарный вес (лайк = 3, прослушивание = 1), показываются
только жанры с двумя и более артистами, топ-8 по весу.

Тегируются верхние 120 артистов библиотеки (один iTunes-запрос и/или один
запрос Яндекса на артиста, 5 параллельно, ~9 с один раз). Кэш
`%APPDATA%/Undertow/genres.json`, TTL 120 дней.

`flow.start(genre?)` при выбранном жанре оставляет в семенах только его
артистов; соседи по графу `related` проходят фильтр «свой жанр или
неизвестно» — неизвестных пускаем, потому что они соседи по похожести и почти
всегда в теме, а тегировать всех соседей слишком дорого. `expand()` второго
круга использует тот же фильтр. Если в жанре нет ни одного артиста из
библиотеки — честная ошибка с названием жанра.

В интерфейсе над кнопкой — чипы `всё · хип-хоп 78 · рок 10 · поп 14…` с числом
артистов; клик сразу пересобирает поток. Выбранный жанр запоминается в
`rec-prefs.json` (`flowGenre`) и после перезапуска чип уже подсвечен, так что
«Запустить» продолжает тот же жанр; «всё» сбрасывает выбор. Источник выбора
для подсветки: выбор в текущей сессии → жанр активного потока (`flow:info`) →
сохранённое значение (`flow:genres`). В шапке живого блока подпись
«сейчас играет · рок».

**Первый трек радио.** Раньше `start()`/`startLocal()` отдавали первые 14
треков артиста как есть — каждый запуск начинался с одного и того же хита.
Теперь `variedSeed()` берёт верх списка (24), перемешивает его и не даёт
первому треку совпасть с предыдущим запуском того же артиста (`lastFirst`).
Соседи тоже выбираются из верхушки списка, но в случайном порядке, а
`interleave` начинает очередной круг с разного пула (`session.turn`), так что
и после первых 14 треков порядок артистов не повторяется. Проверено: шесть
запусков подряд — пять разных первых треков (Skillet), у Яндекса (Rae
Sremmurd) — четыре разных.

Ограничение осталось только физическое — каталог похожих артистов: замер на
MACAN дал 90 + 206 треков, после чего `radioMore` возвращает пустой массив и
радио просто заканчивается (≈16 часов музыки).

## 4j. Всё работает и без Яндекс Плюса

Требование: ни одна новая функция не должна зависеть от подписки. Правило
прежнее — без токена/Плюса Яндекс выключен целиком (никаких 30-секундных
превью), поэтому «без Плюса» = «только YouTube».

Главное открытие: **youtubei.js умеет не только ленту**. `Music.search(name,
{type:'artist'})`, `Music.getArtist(id)` и `Music.getAlbum(id)` отдают ровно то,
что раньше давал Яндекс: топ-треки (не 5 видимых, а 50–100 — через endpoint
кнопки «ещё»), настоящие альбомы с id `MPREb…` и «Похожие исполнители» (10).
Звук по-прежнему берётся через yt-dlp — SABR-ссылки youtubei.js для плеера
не годятся, но метаданные работают без токена и без PO-token.

**Метаданные** (`src/main/providers/youtube.ts`, раздел «YouTube Music»):
`musicSearchArtist`, `musicArtist`, `musicAlbum` + кэш на 30 минут. Обложки в
списках приходят 60×60 — заменяем размер в URL на 544×544. Трек из этих
ответов несёт `artistId` (канал `UC…`), `artists[]` (с id) и, если это страница
альбома, `album`/`albumId = yt-album:<MPREb…>` — поэтому «пластинка» в строке и
ссылки на исполнителей работают и без Яндекса.

**Ссылки-цели вместо id.** Страницы и радио принимают объект
`{ id?, name?, title? }` (`PageRef`). С Яндексом работает id, без него — id
YouTube Music или имя через поиск. `musicArtist` понимает и `UC…`, и
`yt-artist:UC…`, а если id окажется Topic-каналом — молча ищет по имени.

**Страницы артиста/альбома** (`src/main/browse.ts`):
- артист: имя + аватар, топ-треки (до 100), сетка альбомов и «Похожие
  исполнители» — кружки-карточки, каждая открывает свою страницу;
- альбом: настоящий альбом по `MPREb…` (год, артист, треки с длительностями),
  шапка вида `YASMI · 2025 · 16 треков`;
- запасные пути: если артист не нашёлся, работает старый поиск yt-dlp.

**Длительности.** `MusicResponsiveListItem.duration` — это объект
`{ text: '3:45', seconds: 225 }`, а не строка. Общий `parseDuration` сначала
приводил его к строке и получал `"[object Object]"`, из-за чего на страницах
артиста, альбома и в новых строках поиска длительность была пустой («—»).
Теперь берётся `seconds`, затем `text`, затем строка. Старые записи истории
(сохранённые до починки) дозаполняются в фоне: `providers.backfillDurations()`
по `yt.getBasicInfo()` батчами по 40, максимум 240 треков за запуск, с
патчем в `library.json`; после этого сбрасывается кэш главной, а main шлёт
`library:durations`, по которому рендерер перечитывает главную и библиотеку.

**Поиск альбома по названию** (`musicAlbumByTitle`, `musicAlbumOfTrack`).
У «пластинки» в строке часто есть только яндексовский номер альбома, а он без
Плюса бесполезен. Порядок (`youtubeAlbumPage`):
1. `MPREb…` в `albumId` — сразу настоящий альбом;
2. `Music.search(..., {type:'album'})` по «первый артист + название» и профиль
   артиста (альбомы + синглы) с выбором по похожести названия;
3. `musicAlbumOfTrack` — поиск **самого трека** (`{type:'song'}`) и альбом из
   его строки (`album.id = MPREb…`). Это спасает старые альбомы: у артиста в
   профиле видно только 5–7 последних карточек, а `Music.getArtist` не отдаёт
   endpoint «показать все альбомы» (проверено: `endpoint === undefined`);
4. если и там нет — поиск yt-dlp, но выдача чистится: при наличии трека
   остаются только его версии (`titleKey`), в любом случае только строки этого
   артиста (`byArtist` по словам, а не по подстроке) и не больше восьми.
   Подпись честная: `артист · версии трека · YouTube · N треков`.

Сравнение названий — **по словам** (`titleScore` в `youtube.ts`), а не по
`includes`: раньше «AM» у Arctic Monkeys «находился» внутри «Damn Look At These
Massive Brit Hits Vol.19» и пластинка открывала чужой сборник. Теперь 100 —
точное совпадение, 60 — одно название продолжает другое (`Сокровище` ↔
`Сокровище (Deluxe)`), 40 — все слова искомого есть в найденном.

**Проверка «наш ли альбом»** (`albumFits` в `browse.ts`): после загрузки
страницы по найденному id сверяем артиста — по подписи шапки и по первым
восьми строкам. Если в шапке артист есть, а в треках его нет — альбом чужой,
цепочка продолжается. Так отсекается «Ghost» от VYNX PHONK на запрос
phonk.me и «Brit Hits» на запрос Arctic Monkeys. Названию верим только когда
про артиста в шапке ничего нет (там бывает просто `2019 · 10 треков`).

**Автор строк альбома.** `Music.getAlbum` не отдаёт исполнителя ни в строках,
ни в `subtitle` («Альбом • 2017»), зато он есть в `header.strapline_text_one`
(«NF»). Плюс `artistFromSubtitle` больше не берёт первый сегмент подписи, если
это тип (`Альбом`, `Сингл`, `EP`, …) — из-за этого раньше в колонке артиста
стояло «Альбом» или «YouTube».

**Открытие альбома из трека.** Вместе с `id/title/artist` из строки и плеера
уходит `trackTitle` (`page:album` → `providers.albumPage`): по нему работает
и поиск альбома, и чистка запасной выдачи. Из карточек главной `trackTitle`
нет — там альбом ищется только по названию.

**Замер по библиотеке (20 треков из разных глубин, без Плюса):** 16 открывают
настоящий альбом YouTube Music, 4 — честную страницу «версии трека» из 1–2
строк; среднее время 1.9 с, «солянки» из 20 строк больше нет.

**Радио** (`radio.ts`) в режиме без Плюса теперь такое же, как с Яндексом:
1. `musicArtist(seed)` → 14 своих треков в начало;
2. `related` → 7 соседей, у каждого забираем весь список топ-треков (≈100);
3. чередование по кругу → 90 уникальных треков;
4. когда пулы кончились — второй круг: `related` у четырёх соседей
   (`RING2_PICKS`), это ещё ~400 треков. Профили соседей уже в кэше, так что
   расширение почти бесплатное;
5. `radio:more` отдаёт по 30 треков, очередь дописывается через
   `engine.appendQueue`.

Замер без Плюса: старт 2.7 с, 90 треков, 48 разных исполнителей; дозаправки
90 → 120 → 150, все уникальные, 72 исполнителя. Библиотека больше не участвует
в подборе — только как источник лайков для секций «Ещё от…».

**Главная без Яндекса** — `recommend.localHome()`: локальные секции
(продолжить/давно не слушали) + до двух «Ещё от <артист>» из топ-треков
YouTube Music; id секции `rec-artist-name:<urlencoded>` — по нему работают и
ссылка «артист →», и «скрыть секцию». Кэш в памяти на 6 ч.

**Карточки YouTube на главной**: у альбомов берём настоящий `MPREb…` из id
(`yt:MPREb…`) и открываем альбом, а не поиск; у остальных — имя артиста или
заглушка «скоро».

**Мелкая чистка выдачи.** `youtube.search` помечает неиграбельными каналы и
плейлисты (`UC…`, `PL…`, `RD…`, длина ≠ 11): yt-dlp на такой «трек» отвечает
`This video is unavailable`.

## 4k. Жанры, плейлисты, тексты, «похожее» и поиск по разделам

**Жанры** (`genres.ts`). Жанровые теги кэшируются в `genres.json` (TTL 120
дней) и собираются гибридно: сначала жанр артиста из Яндекса
(`/artists/{id}.genres`), иначе — из iTunes Search API. Названия приводим к
14 фиксированным бакетам (`BUCKETS`), чтобы в чипах не появлялось «Зимние
праздники». `list()` отдаёт только жанры, где ≥2 артиста, топ-8 по весу;
`detail(id)` — тот же жанр плюс топ-24 артиста из лайков/истории с обложкой
и `artistId`. Экран: сетка карточек → страница жанра с кнопками «Слушать
всё» (запускает `flow:start(genre)`) и переходом на артиста. Всё без Плюса.

**Плейлисты** (`playlists.ts`). Отдельный `playlists.json`, до 200 списков по
3000 треков, дубликаты внутри списка отсекаются по `id`. В файле лежат копии
треков, поэтому плейлист открывается без сети и не зависит от того, жив ли
трек в источнике. IPC: `playlists:list/get/create/rename/remove/add/
remove-track/reorder/import/export`. Импорт из Яндекса
(`/users/{uid}/playlists/list` + `/users/{uid}/playlists/{kind}?rich-tracks=true`)
пропускает плейлисты с уже существующим названием; важно, что rich-tracks
кладёт трек внутрь обёртки `{ id, timestamp, track: {...} }` — раньше из-за
этого импортировались пустые списки. Экспорт — диалог сохранения JSON через
`dialog.showSaveDialog`. В списках у каждой строки есть «в плейлист»
(модальный выбор + создание на месте), строки плейлиста перетаскиваются,
удаляются и играются как очередь.

**Тексты** (`lyrics.ts`). LRCLIB без токена: сначала точный `/api/get` по
артисту/названию/длительности, затем `/api/search` с оценкой по совпадению
названия, артиста и близости длительности. LRC парсится в `{t, text}`
(поддержка нескольких меток в строке), текст без таймингов показывается как
обычный, инструментал — отдельной пометкой. Кэш в памяти на 7 дней, в том
числе отрицательный. Панель в плеере подсвечивает активную строку по
`snap.time`, клик по строке перематывает (`engine.seek`).

**«Похожее» на трек** (`radio.similar`). Для яндексового трека —
`/tracks/{id}/similar` (≈16–30 штук), для YouTube — `music.getUpNext(videoId)`
(≈50 строк `PlaylistPanel`, у них id лежит в `video_id`, а не в `id`). Если
набралось меньше 18 треков, добиваем радио артиста (Яндекс или
`startLocal`) и отдаём до 60. Очередь одноразовая: авто-дозаправка включается
только у радио артиста.

**Поиск по разделам** (`youtube.musicSearchAll`). Три параллельных запроса
`music.search(q, {type:'song'|'album'|'artist'})`, разбор через
`collectItems` + `musicTrack`/`albumRefOf`/`artistRefOf`. Провайдер
`searchAll` берёт треки из Яндекса, когда он активен (качество и метаданные
лучше), и всегда добавляет альбомы/артистов из YouTube Music; дубликаты
между источниками отсекаются по `название|артист`. Экран поиска показывает
кружки исполнителей, карточки альбомов (клик открывает `yt-album:MPREb…`) и
список треков.

**Окно в dev на втором мониторе.** `placeOnSecondDisplay()` в
`src/main/index.ts` при `!app.isPackaged` находит не-основной дисплей
(`screen.getAllDisplays`) и центрирует окно в его рабочей области, ужимая
размер под неё. Собранное приложение этим не пользуется.

## 5. Яндекс.Музыка: что нужно знать

**Правила включения (заданы пользователем):**

| Состояние | Поведение |
|---|---|
| токена нет | только YouTube |
| токен есть, Плюса нет | только YouTube, Яндекс выключен (без превью по 30 с) |
| токен есть, Плюс активен | Яндекс основной, YouTube добирает (2 секции в ленте, 12 результатов в поиске) |

Если Яндекс всё же вернул превью вместо трека — провайдер сам себя гасит
до ручной перепроверки в настройках.

- Авторизация: OAuth-токен из настроек (ввод один раз, хранится в
  `%APPDATA%/Undertow/secrets.json`; в БД не пишем).
- Заголовки: `Authorization: OAuth <token>`, `X-Yandex-Music-Client: YandexMusicDesktopAppWindows/5.13.2`.
- `GET /get-file-info` — параметры `ts, trackId, quality, codecs, transports, sign`,
  где `sign = base64(hmac_sha256(secret, ts+trackId+quality+codecs+transports))[:-1]`,
  secret — публичный ключ клиента. Ответ — `downloadInfo.urls[]` (живут ~1 минуту).
- Качество: `lossless` (flac/flac-mp4), `high` (aac 320), `normal`.
- Старый путь `DownloadInfo.get_direct_link()` (XML + `sign = md5(salt + path[1:] + s)`)
  ещё работает для MP3 и проще в отладке.

**Это единственный реальный блокер прямо сейчас: нужен мой токен.**

## 6. Хранение

`better-sqlite3`, файл `%APPDATA%/Undertow/library.db`:

- `tracks`, `artists`, `albums`, `playlists`, `playlist_items` — кэш метаданных,
  чтобы «Моя музыка» открывалась мгновенно и работала без сети;
- `history` (что играло, когда, сколько секунд) → «недавние» и рекомендации;
- `liked` — сердце;
- `settings` — провайдер, качество, тема, аудиовыход.

Обложки — в `%APPDATA%/Undertow/cache/covers/` (хэш URL → файл, TTL 30 дней).
Аудио-кэш (офлайн) — отдельная папка, включается в настройках.

## 8. Порядок работ

1. ✅ Спайк: доказан стрим (YouTube через yt-dlp, 206 OK). `spikes/ytmusic.mjs`
2. ✅ Каркас Electron + React + TS, окно с нативной полосой, тема, роутинг.
3. ✅ Провайдер YouTube: лента (youtubei.js), поиск (yt-dlp flat), звук (yt-dlp -g).
   Проверено в живом окне: resolve → play → перемотка → автопереход.

6. Красота: страницы альбомов, анимации, мини-плеер, горячие клавиши, трей.
